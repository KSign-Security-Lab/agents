문서 기반 에이전트 · COMPOSE_PROFILES

One GPU server serves the models.
Your laptop runs everything else.

Nothing you run locally needs a GPU, so this works on a Mac. The two services that need CUDA live on the shared box; the two services you actually edit run on your host with hot reload.

What each piece is

gpu

COMPOSE_PROFILES=gpu

Three services. vllm and infer are the two that need CUDA, which is the entire reason this profile isn't local.
ServiceRuns asWhat it does
llm-gateway nginx · :8602 The one URL the application knows. Whether there's one replica behind it or two is deployment config: adding the replica2 profile puts a second replica behind it without the application noticing.
vllm container · :8000 internal Serves EXAONE-4.0-32B-AWQ. Writes the answers and emits the tool calls the agent's query planning depends on.
infer container · :8603 Three models in one VRAM budget: bge-m3 embeds (one pass gives both the dense vector and the sparse lexical weights, so hybrid search needs no second model), bge-reranker-v2-m3 rescores the shortlist, and faster-whisper transcribes recordings.
dev

COMPOSE_PROFILES=dev, plus two host processes

Nothing here needs a GPU, so all of it runs on your laptop.
ServiceRuns asWhat it does
postgres container · :5433 pgvector. Documents, chunks, the branching message tree, and both vector columns — vector for dense, sparsevec for lexical. Also holds chunk_spans, the text-offset → page-rectangle map that makes citations clickable.
redis container · :6380 The ingest queue. api enqueues an upload; the worker consumes it.
api host · :8000 · reloads FastAPI + LangGraph: the agent, SSE streaming, citation resolution. Carries no torch at all — every GPU call goes out over HTTP — which is why it runs on your host instead of in a container.
web host · :3000 · reloads Next.js UI, and the proxy in front of it: the browser never sees the API, it holds an httpOnly cookie and this tier attaches the token server-side.
worker container · opt-in convert → extract → chunk → embed → categorize. LibreOffice, H2Orestart for HWP, PyMuPDF, OCR and ffmpeg are why this image is large, so it only starts with docker compose up -d worker — you need it to debug ingest, not to work on chat.

What to run, on which machine

GPU server

Once, by whoever owns the box — then again only after a reboot.

First time

cp .env.example .env
$EDITOR .env    # COMPOSE_PROFILES=gpu
                # VLLM_A_GPUS, BIND_ADDR

Serve it

docker compose up -d
docker compose logs -f vllm-a
docker compose config --profiles  # what else exists

No Postgres, no Redis, no web, no worker on this box — the gpu profile selects only these services out of compose.yaml.

Your machine

Every developer, on their own laptop.

First time

cp .env.example .env
$EDITOR .env    # COMPOSE_PROFILES=dev, GPU_HOST

Every day

# only if the GPU box stays on loopback
ssh -N -L 8602:localhost:8602 \
       -L 8603:localhost:8603 gpu-host

pnpm install && pnpm venv
pnpm dev

Starts the containers, migrates, seeds dev@agents.dev / devdev, then runs api and web with reload. Ctrl-C stops the two processes and leaves the containers up, so the next run takes seconds.

Running less than everything

CommandStartsReach for it when

There is no third mode

One compose file, and COMPOSE_PROFILES says what this machine is. The gpu profile needs CUDA; dev needs nothing but Docker. They're independent, so if you want everything on one machine you run both — there is no separate all-in-one path to learn, and no combined stack that can drift from what developers actually run.

Config is one file: .env at the repo root, copied from .env.example. Compose reads it, and so does apps/api/app/config.py, which assembles the database and model URLs from it.
